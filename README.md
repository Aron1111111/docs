# 图书俱乐部文档项目 / Документация Книжного клуба

## 1 项目用途 / Назначение проекта

bookclub-docs 用于软件生命周期课程，组织图书俱乐部的需求、架构、接口、测试设计和操作指南，并练习 A、B 两人使用 Git 协作。
bookclub-docs используется в курсе жизненного цикла ПО: требования, архитектура, API, проектирование тестов и руководства Книжного клуба, а также совместная работа A и B в Git.

本仓库包含文档源文件与文档检查脚本，尚未包含可部署的图书俱乐部业务应用。
Репозиторий содержит исходники документации и скрипт её проверки; развёртываемого бизнес-приложения здесь пока нет.

## 3 打开与检查文档 / Просмотр и проверка документации

用 VS Code 或 PyCharm 打开整个 bookclub-docs 文件夹，再打开 README.md 的 Markdown 预览。点击上表的相对链接，检查文字、表格及两张图片。
Откройте всю папку bookclub-docs в VS Code или PyCharm, затем предпросмотр README.md. Проверьте относительные ссылки, текст, таблицы и два изображения.

文档网站构建尚未配置：没有 Sphinx 的 conf.py 和构建依赖清单。本阶段直接预览 Markdown，不使用未配置的构建命令。
Сборка сайта пока не настроена: нет conf.py Sphinx и файла его зависимостей. На этом этапе используется предпросмотр Markdown.

以下命令在仓库根目录的终端执行。check_docs.py 仅使用 Python 标准库，检查本地文件引用、路径范围、必需文件和 PNG 文件头，不会启动业务应用。
Выполните команды в терминале корня проекта. check_docs.py использует только стандартную библиотеку Python и проверяет локальные ссылки, границы путей, обязательные файлы и заголовки PNG. Бизнес-приложение не запускается.

```text
python tools/check_docs.py
git diff --check
```

Windows 中若 python 命令不可用，可改用 py tools/check_docs.py。正确结果为脚本输出 PASS 且退出码为 0；git diff --check 无错误且退出码为 0。
В Windows при отсутствии команды python используйте py tools/check_docs.py. Успех: PASS и код 0; git diff --check завершается без ошибки с кодом 0.

## 4 分支与协作顺序 / Ветки и порядок работы

main 保存已评审的版本；A 使用 docs/user-guide 分支修改用户指南，B 使用 docs/admin-guide 分支修改仓库管理员指南。
main содержит проверенные версии. A изменяет руководство пользователя в ветке docs/user-guide, B — руководство администратора в docs/admin-guide.

1. A 创建并推送初始仓库，B 随后使用自己的账号克隆。双方分别配置提交身份并执行命令，不只观察同伴。
   A создаёт и отправляет исходный репозиторий, затем B клонирует его под своей учётной записью. Каждый сам настраивает автора и выполняет команды.
2. 工作区干净时切换到 main 并同步，再新建自己的工作分支。以下 A、B 命令是二选一，按角色执行。
   При чистом рабочем дереве перейдите на main, обновите его и создайте свою ветку. Выберите команду A или B, не обе сразу.

```text
git switch main
git pull --ff-only origin main
```

A 首次创建分支 / A создаёт ветку впервые:

```text
git switch -c docs/user-guide
```

B 首次创建分支 / B создаёт ветку впервые:

```text
git switch -c docs/admin-guide
```

已有分支直接用 git switch 分支名进入，不再次使用 -c。
Для существующей ветки выполните git switch с её именем без -c.

3. 修改自己的文件，运行文档检查和 git diff --check，查看 git diff；只暂存需要的文件，再提交并推送自己的分支。
   Измените свой файл, проверьте документацию, git diff --check и git diff. Добавьте нужные файлы, создайте коммит и отправьте свою ветку.
4. 发起合并到 main 的 Pull Request，由同伴检查后合并。之后双方同步 main。当前尚未实际执行在线 Pull Request。
   Создайте Pull Request в main; партнёр проверяет изменения перед слиянием. Затем обновите main. Онлайн Pull Request пока не выполнялся.

完整初始化、推送和克隆命令见 COLLABORATION.md。远程地址必须由 A 提供，不能把示例地址当作真实仓库。
Команды инициализации, отправки и клонирования находятся в COLLABORATION.md. Настоящий адрес предоставляет A.

## 6 不入库的内容 / Что не хранится в репозитории

不提交 .env、真实密码和令牌、私钥、个人数据、虚拟环境、缓存、生成网站、日志、本地数据库及编辑器个人设置。图像源文件和 API 规范应保留在仓库。
Не коммитить .env, настоящие пароли и токены, закрытые ключи, персональные данные, виртуальную среду, кэш, сайт сборки, журналы, локальные базы и личные настройки редактора. Изображения и API остаются в репозитории.

规则见 .gitignore 和 STORAGE_POLICY.md。首次 add 前逐项检查文件；.gitignore 不会清除已跟踪文件或历史中的秘密。
Правила указаны в .gitignore и STORAGE_POLICY.md. До первого add просмотрите файлы: .gitignore не удаляет уже отслеживаемые секреты и историю.

压缩包不包含 .git，不复制其他项目的历史。A 初始化，B 通过 clone 获取该项目历史。
Архив не содержит .git. Не копируйте историю другого проекта: A инициализирует репозиторий, B получает его через clone.

# 仓库管理员指南 / Руководство администратора репозитория

维护角色 B。本指南管理文档仓库；不提供尚未实现的业务服务启动或数据库恢复命令。
Ответственный — B. Руководство относится к документации; команды запуска бизнес-сервиса и восстановления его базы здесь не определены.

## 接收项目 / Получение проекта

前提：A 已创建并推送仓库，B 已获得访问权限。B 使用自己的账号和身份执行 git clone，然后检查 README、两份指南、图像和 API 文件。
Условие: A создал и отправил репозиторий, у B есть доступ. B клонирует его со своей учётной записью и проверяет README, руководства, изображения и API.

预期：克隆成功且 git status 显示工作区干净。失败时检查 URL、权限和网络，不将密码写入远程 URL。
Ожидаются успешное клонирование и чистое рабочее дерево. При ошибке проверьте адрес, доступ и сеть; пароль не включайте в URL.

## 检查文档 / Проверка документации

前提：在仓库根目录。预览 README 和所有 Markdown，点击相对链接并确认两张图显示。运行 git diff --check 检查空白问题。
Условие: открыт корень репозитория. Просмотрите Markdown, проверьте ссылки и два изображения. Команда git diff --check проверяет ошибки пробелов.

预期：引用目标存在，页面和图片可读。失败时修正相对路径；禁止使用个人电脑的绝对路径。
Ожидаются существующие цели ссылок и читаемые страницы. При ошибке исправьте относительные пути; локальные абсолютные пути не используйте.

## 保存修改与恢复 / Сохранение и восстановление

前提：已确认当前分支和工作区。先查看 git diff，提交时逐项选择文件；不要覆盖同伴未提交的修改。
Условие: проверены ветка и рабочее дерево. Просмотрите git diff и выберите файлы для коммита. Не перезаписывайте несохранённую работу партнёра.

需要恢复时，先把当前修改另存为补丁或副本，再从已确认的提交恢复所需文件。已共享的错误提交优先用 git revert 创建反向提交，并再次检查页面。
Перед восстановлением сохраните текущие изменения в патч или копию. Затем восстановите нужный файл из проверенного коммита. Общий ошибочный коммит предпочтительно отменять через git revert с повторной проверкой страниц.
